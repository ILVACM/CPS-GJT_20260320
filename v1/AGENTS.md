## 1. 项目概述

### 1.1 项目目标

研制一款基于边缘计算的钢筋直径测量设备：由深度相机采集现场画面，AI 语义分割识别图中钢筋，结合激光测距完成像素到物理尺寸的换算，自动输出每根钢筋的直径（就近对齐国标规格）与相邻间距，并在本地实时显示叠加了测量结果的画面。

### 1.2 产品定位

- 部署形态：双节点边缘盒子，本地闭环运行，不依赖外网与云端
- 应用场景：施工现场 / 质检环节的钢筋直径、间距自动化检测
- 关键指标：原型阶段不定量（属 C 类要素，正式开发阶段制定）

### 1.3 技术栈概览

| 层次 | 选型 |
|------|------|
| 开发语言 | Python 3 |
| AI 模型 | PyTorch，UNet（ResNet50 backbone，3 类语义分割，输入 640×640） |
| 视觉与测量 | OpenCV、NumPy |
| 节点间通信 | gRPC（Protocol Buffers） |
| 深度相机 | Orbbec Gemini 336L（双目，RGB + Depth） |
| 激光测距 | 轮趣科技 STP23L 激光单点测距探头 ×4 → 轮趣 S21C 主控板汇总，Type-C 转 USB 串口接入服务节点 |
| 本地 GUI | tkinter（服务节点） |
| 操作系统 | 检测节点：Ubuntu 22.04 LTS；服务节点：openEuler 22 LTS |

## 2. 系统架构与硬件环境

### 2.1 双节点架构

设备原型由两块边缘开发板组成，每块板为一个独立节点，AI 推理负载与系统调度负载物理隔离。

设计理由（Why）：

- **性能冗余与隔离**：UNet 推理计算密集，若与视频采集、画面渲染、串口通信、用户交互共板运行，资源争抢会导致掉帧与 UI 卡顿；物理隔离后两类负载互不干扰
- **独立演进**：推理节点可单独更换硬件或升级模型，主控逻辑不受影响
- **故障域隔离**：推理服务崩溃不阻塞采集与显示主流程，系统可降级运行

硬件选型依据：

- 检测节点 选 Jetson Nano：板载 CUDA GPU，可硬件加速 PyTorch 推理，是低成本的入门 AI 计算板，算力与"专用推理"职责匹配
- 服务节点 选 OrangePi KunPeng：主控不需要 GPU 算力，但需要稳定的多外设接入（USB 相机、UART 探头、显示输出）与 openEuler 生态

```
[深度摄像机 336L] ─────────RGB/Depth──────────┐
                                                ↓
[STP23L ×4] ──UART──→ [S21C 主控] ──Type-C 串口──→ [服务节点 主控] ──图像数据──→ [检测节点 AI推理]
                                                         ↑                        │
                                                         └───── 推理结果 ─────────┘
                                                         │
                                                         ↓
                                               [测量换算 / 画面拼接 / 显示 / 交互]
```

### 2.2 检测节点 — AI 推理节点（Jetson Nano）

| 属性 | 说明 |
|------|------|
| 硬件 | NVIDIA Jetson Nano |
| 操作系统 | Ubuntu 22.04 LTS（NVIDIA Jetson 官方定制内核，原生兼容 CUDA 生态，已配置完毕） |
| 角色 | 专用 AI 计算节点，gRPC 服务端 |
| 核心职责 | 加载 UNet 分割模型，对接收到的图像执行推理 |
| 输入 | 服务节点 发送的 RGB 图像 |
| 输出 | 分割掩码（0=背景 / 1=纵向钢筋 / 2=横向钢筋）及标注数据 |

职责边界：检测节点 只做推理，**不做**物理测量换算；gRPC 请求中携带的距离标量仅随帧记录（用于日志追溯与帧同步校验），不参与任何计算。理由：测量换算在数据使用方（服务节点）执行，检测节点 无需持有相机内参与传感器状态，保持无状态、可替换。

推理逻辑流程（源自 `new-predict.py` 的 `Unet` 类）：

1. **输入**：单张 RGB 彩色图像（任意尺寸，PIL/numpy 均可承接）
2. **预处理**：等比缩放装入 640×640 输入框（长边缩放、短边不足填灰边，画面不变形）→ 按 ImageNet 均值/方差标准化 → 转为 [1, 3, 640, 640] 张量
3. **前向推理**：UNet（ResNet50 backbone）输出每个像素分属 3 类的概率分布
4. **后处理**：裁掉灰边区域 → 插值放大回原图尺寸 → 逐像素取概率最大的类别
5. **输出**：与原图同尺寸的单通道 uint8 掩码，像素取值 0/1/2（0=背景，1=纵向钢筋，2=横向钢筋）；`detect_label` 即返回该掩码，`detect_image` 则返回着色后的可视化分割图（供调试）

## 3. 模块化设计指引

### 3.1 模块划分总览

检测节点 与服务节点 各自内部按高内聚低耦合原则划分独立模块，模块间仅经明确接口交互，禁止跨模块直接读写内部状态：

| 节点 | 模块（命名空间） | 职责 |
|------|------------------|------|
| A | `inference` | UNet 模型加载与前向推理 |
| A | `grpc_server` | gRPC 服务端，在 A:50051 提供 Infer RPC（S→D） |
| A | `grpc_client` | 主动向服务节点 发送 Heartbeat（周期）+ Shutdown（一次性），方向 D→S |
| A | `system` | 启停与环境自检（见 §4.3） |
| B | `camera`（输入模块） | 深度相机采集，面向接口抽象（见 §3.2） |
| B | `serial` | 串口通信与激光数据解析、有效性检查 |
| B | `grpc_client` | gRPC 客户端，向检测节点 发送 Infer 推理请求、接收结果（S→D） |
| B | `grpc_server` | gRPC 服务端，在 B:50051 接收检测节点 的 Heartbeat + Shutdown RPC，转交 NodeMonitor 处理（D→S） |
| B | `measure` | 测量换算（直径/间距）与内参管理 |
| B | `ui` | tkinter 界面交互、画面渲染与激光融合策略 CLI 菜单 |
| B | `system` | 启停、环境自检与降级调度（见 §4.3） |

共享常量（串口帧格式、分割类别定义、国标规格表、通信 proto）集中定义、单一来源，双节点禁止各自硬编码副本。

### 3.2 输入模块抽象（Input Module）

**设计目标**：将深度相机输入整合为独立模块，采用面向接口编程（抽象基类），336L 作为接口的一个具体实现。此举使相机层可替换、可扩展（未来引入深度信息流或更换设备型号时，仅需新增实现类，上层逻辑无需改动）。

**接口定义（架构级）**：

```
BaseCameraInput（抽象基类）
  ├── open() -> bool              # 打开设备
  ├── close() -> None             # 关闭设备
  ├── is_opened() -> bool         # 设备是否就绪
  ├── get_rgb_frame() -> np.ndarray | None    # 获取一帧 RGB 图像
  ├── get_depth_frame() -> np.ndarray | None  # 获取一帧 Depth 深度图（原型阶段可不实现，返回 None）
  └── get_intrinsics() -> dict    # 获取相机内参（fx, fy, cx, cy）

Orbbec336LInput(BaseCameraInput)
  # 基于 Orbbec SDK 的具体实现
  # 所有参数（分辨率、帧率等）从 JSON 配置文件读取（见 §3.3）

# 未来扩展示例（原型阶段不实现）：
# class MockCameraInput(BaseCameraInput): ...     # 服务节点 独立联调用
# class DepthFusionInput(BaseCameraInput): ...    # 引入深度信息流
```

**与现有代码的关系**：`demo.py` 的 `CameraManager` 是针对普通 USB 摄像头的实现，需重构为 `Orbbec336LInput` 的具体实现；`CameraManager` 中的线程模型（后台读帧、断线重连）保留复用，纳入输入模块内部。

### 3.3 配置文件管理

本项目所有值类参数均从 JSON 配置文件读取，严禁硬编码。配置文件分类如下：

| 配置文件 | 内容 | 使用节点 |
|----------|------|----------|
| `config/camera.json` | 336L 相机参数：RGB/Depth 分辨率、帧率、色彩格式等 | 服务节点 |
| `config/intrinsics.json` | 相机内参：fx, fy, cx, cy（默认 fx=fy=950，见 §8.3） | 服务节点 |
| `config/network.json` | 网络参数：本机 IP、对端 IP、gRPC 端口号、心跳间隔（`heartbeat_interval_seconds`，默认 5）、超时阈值（`heartbeat_timeout_count`，默认 3）、网络动态监测周期（`network_monitor_interval_seconds`，默认 5.0，见 §4.3）（见 §4.2） | 双节点（各持一份） |
| `config/inference.json` | 推理节奏参数：`inference_interval_seconds`（默认 3.0）——服务节点 侧控制相邻两次推理请求的最小时间间隔 | 服务节点 |
| `config/serial.json` | S21C 串口参数：设备路径/自动扫描白名单/波特率/热插拔扫描间隔（`scan_interval_seconds`，默认 2.0，见 §6.1）等 | 服务节点 |

配置文件格式与具体字段定义在开发时按实际需求细化。

`config/inference.json` 示例：
```json
{
  "inference_interval_seconds": 3.0
}
```

**控制权归属（已定稿）**：推理请求的最小时间间隔**仅在服务节点 侧执行**——服务节点 的 UI / 调度模块在收到用户触发后，先读取本配置值进行时间戳门控，未达间隔时阻止请求发出。**检测节点 侧不做任何时间间隔检查**——推理端以实际处理能力为上限，收到请求后即刻执行推理，"能跑多少跑多少"。

## 4. 网络拓扑、配置管理与启动自检

### 4.1 网络拓扑（已定稿）

双节点**网线直连**，配置**静态 IP** 与**固定 gRPC 端口**，形成点对点私有网络：

- 检测节点（Jetson Nano）：静态 IP（如 `192.168.10.2`），在 A:50051 监听 gRPC 服务端，提供 Infer RPC（S→D 方向）
- 服务节点（OrangePi）：静态 IP（如 `192.168.10.1`），在 B:50051 监听 gRPC 服务端，提供 Heartbeat + Shutdown RPC（D→S 方向）；同时作为 gRPC 客户端向检测节点 发起 Infer 调用
- 检测节点 同时作为 gRPC 客户端向服务节点 周期发送 Heartbeat 并在退出时发送 Shutdown
- gRPC 端口：默认 `50051`（业界惯例值，可经配置文件调整）；**双节点各自在 50051 监听，通过对方静态 IP 寻址对端 50051，双方向各持独立 gRPC channel，禁止复用同一 channel 承载双向调用**

具体 IP 地址段与端口号在 `config/network.json` 中配置，部署前由人工分配写入。

### 4.2 网络参数配置化

静态 IP 地址与 gRPC 端口号均从 `config/network.json` 读取，检测节点 与服务节点 各持一份。配置示例：

```json
{
  "local_ip": "192.168.10.1",
  "remote_ip": "192.168.10.2",
  "grpc_port": 50051,
  "heartbeat_interval_seconds": 5,
  "heartbeat_timeout_count": 3,
  "network_monitor_interval_seconds": 5.0
}
```

**IP 设置方式（已定稿）**：采用**独立的网络配置脚本**（Shell 脚本，需 root 权限执行）在部署时一次性设置系统静态 IP；应用程序启动时**仅做校验与警告**，不通过代码直接修改系统网络配置。理由：修改系统 IP 需要 root 权限，在应用代码中调用 `ip`/`ifconfig` 命令既不安全也不可移植；独立脚本一次配置、反复使用，应用层只负责"环境是否就绪"的判断。

### 4.3 启动环境自检机制

程序启动时（UI 初始化之前）必须执行环境自检。**网络相关项采用诊断模式（仅记录日志，不阻断启动）**，由运行时 `NetworkMonitor` 接管动态监测；仅配置文件加载失败（真正致命）才安全退出：

| 检查项 | 检测节点（服务端） | 服务节点（客户端） | 失败处理 |
|--------|------------------|------------------|----------|
| **本机 IP 校验** | 检查本机网卡 IP 是否与 `network.json` 中的 `local_ip` 一致 | 同左 | 不一致 → 记录 `[诊断]` 日志，**不退出**，交由 NetworkMonitor 持续监测 |
| **端口可用性** | 检查 gRPC 端口是否未被占用（可绑定） | 检查本地是否无端口冲突 | 不可用 → 记录 `[诊断]` 日志，**不退出**（本地功能正常，推理可能受限） |
| **对端可达性** | — | TCP 探测检测节点 的 IP:端口是否可达 | 不可达 → 记录日志 + 界面提示 + 进入**降级模式**（仅视频 + 激光），由 NetworkMonitor 后台周期探测恢复 |

**与降级模式的关系**：本次迭代**全部放开网络硬故障**——本机 IP 不匹配、端口冲突、对端不可达均不再导致退出，一律记录诊断日志并进入（或维持）运行时状态。服务节点 启动后由 `NetworkMonitor` 后台线程周期探测检测节点 可达性（间隔由 `network_monitor_interval_seconds` 配置，默认 5 秒）；对端不可达时系统降级（仅视频 + 激光 + 本地测量/保存，识别按钮禁用），网络恢复后自动切回在线模式。降级模式界面提示"推理服务离线"，服务节点 仍可独立展示视频预览与激光测距数据。

**与设备扫描的关系**：网络自检为**诊断日志**（不阻塞），在 UI 启动前同步执行；相机与串口设备（S21C）的扫描连接为软前置条件，在 UI 启动后**异步持续进行**（S21C 热插拔扫描），失败可重试（沿用现有约定）。

**与运行时健康检查的关系**：启动自检是一次性诊断（UI 前）；运行中由 `NetworkMonitor`（网络、§5.7）+ `NodeMonitor`（检测节点 心跳）周期探测（UI 后，见 §5.6/§5.7）。对端不可达在启动走降级模式，在运行中走动态监测逻辑，两者衔接一致。

**平台兼容**：Windows 开发调试环境下，IP 校验逻辑需兼容 Windows 网络配置（或提供 bypass 选项）；端口检查逻辑跨平台通用。

## 5. 数据流向与 gRPC 协议规范

### 5.1 采集段（服务节点）

- **相机**：336L 经 USB 接入服务节点，同步输出 RGB 画面与 Depth 深度图；原型阶段仅使用 RGB 通道参与推理与测量，Depth 留作后续精度增强项。相机参数从 `config/camera.json` 读取 [待补充：Orbbec SDK 接入方式与版本、分辨率/帧率具体值]
- **激光**：4 路 STP23L 接入轮趣 S21C 主控板的测距接口一~四，主控汇总后经 Type-C 转 USB 数据线连接服务节点（CH9102 USB 转串口，波特率 115200；主控亦经 Type-C 取电，另支持 CAN 输出，本项目不使用）。STP23L 本体采样率 120Hz，主控例程以 20Hz 频率汇总上报 4 路数据
- **激光帧协议**（《S21C 主控使用说明》§3.1 "Type-C 串口"，与 `demo.py` 现有解析实现一致）：11 字节帧——帧头 `0x7B` + 4 路大端序 uint16 测距值（单位 mm，如 `0x03 0xE8` = 1000mm，依序对应接口一~四）+ 1 字节校验（前 9 字节异或和，手册称 RCC）+ 帧尾 `0x7D`。注：手册协议表中第 8~9 字节误标为"接口二"，依上下文应为接口四

### 5.2 推理段（服务节点 ↔ 检测节点）

1. 服务节点 将 RGB 帧编码后经 gRPC 发送至检测节点
2. 检测节点 解码 → UNet 前向推理 → 输出 0/1/2 类别掩码 → 编码回传服务节点
3. 触发模式为**按需触发**：用户确认测量时执行单帧推理，不做逐帧连续推理。相邻两次推理请求之间的**最小间隔由服务节点 侧配置参数 `inference_interval_seconds` 控制（默认值为 3 秒）**，检测节点 侧不做强制节流——推理端以实际性能为上限，尽可能快地处理收到的请求

### 5.3 测量与显示段（服务节点）

1. **测量换算**：类别掩码 + 距离 → mm/px（mm/px = 距离 ÷ fx）→ 逐根提取钢筋并测直径，就近对齐国标规格（6/8/10/12/14/16/18/20/22/25/28/32/36/40 mm），另计算相邻钢筋间距
2. **距离来源（已定稿）**：当前阶段统一使用**激光单点测距**——S21C 主控将 4 路 STP23L 数据打包为一帧上报服务节点，作为测量帧的工作距离；不使用 336L 的 Depth 深度图参与测量换算（现有算法为"全场统一距离"模型，单标量即可满足；Depth 属后续精度增强项）。4 路测距值的融合策略由 CLI 交互式选择（见 §6.2）
3. **融合显示**：RGB 原图 + 掩码叠加 + 直径/间距标注，拼接渲染后经 tkinter 本地显示；交互操作（触发测量、参数调整等）由主控 GUI 承接

### 5.4 节点间通信：gRPC

理由（Why）：

- protobuf 强类型契约，接口变更可控，双节点并行开发不易跑偏
- 自动生成 Python 桩代码，省去手写编解码与版本对齐成本
- 原生支持流式调用，后续若升级为连续流式推理无需更换框架
- 跨语言：检测节点 未来如需以 C++/TensorRT 重写推理服务，可平滑替换实现

### 5.5 服务与数据格式（原型阶段定稿）

```proto
syntax = "proto3";

package rebar.inference;

service RebarInference {
  rpc Infer(InferRequest) returns (InferResponse);
  rpc Heartbeat(HeartbeatRequest) returns (HeartbeatResponse);
  rpc Shutdown(ShutdownRequest) returns (ShutdownResponse);   // D→S 退出通知（best-effort）
}

message InferRequest {
  bytes image = 1;                 // JPEG 编码的 RGB 帧
  uint32 frame_id = 2;             // 帧序号（单调递增），帧同步主键
  int64 timestamp_ms = 3;          // 采集时刻时间戳（毫秒），帧同步辅助校验
  double camera_distance_mm = 4;   // 拍摄距离标量（激光测距值），随帧绑定
}

message InferResponse {
  bytes label_mask = 1;        // PNG 编码的单通道 0/1/2 类别掩码
  uint32 frame_id = 2;         // 回传请求 frame_id，帧同步主键
  int64 timestamp_ms = 3;      // 回传请求时间戳，供帧同步校验
  uint32 width = 4;            // 掩码宽（与原图一致）
  uint32 height = 5;           // 掩码高（与原图一致）
  NodeStatus status = 6;       // 节点当前状态（闲/忙/退出中）— 状态捎带
}

// ---- 心跳包（极简，协议级 KeepAlive） ----
// 用途：检测节点 主动周期性推送，供服务节点 判定存活性 + 状态同步
// 方向：A → B；服务节点 侧 grpc_server 注册此 RPC
// 体积极小：不含图像/掩码，仅 5 个基础字段（protobuf 编码后 ≈ 30 字节）
message HeartbeatRequest {
  string node_id = 1;          // 节点标识 "node-detect"（便于未来多节点扩展）
  int64 timestamp_ms = 2;      // 发送时刻（毫秒时间戳）
  NodeStatus status = 3;       // 节点当前工作状态
  uint32 infer_count = 4;      // 累计推理成功次数（监控用，可选）
  uint32 last_infer_duration_ms = 5;  // 最近一次推理耗时毫秒（性能观测，可选）
}

message HeartbeatResponse {
  bool accepted = 1;           // 服务端是否受理
  int64 server_timestamp_ms = 2;  // 服务端接收时刻（时钟漂移校验）
}

// ---- 退出通知（Best-effort，D→S 一次性） ----
// 用途：检测节点 退出前主动通知服务节点，使其立即降级，无需等心跳超时
// 方向：A → B；服务节点 侧 grpc_server 注册此 RPC
// 语义：best-effort —— A 侧设短 deadline（2s），超时/失败仅记 WARNING 日志，不重试、不阻塞退出
message ShutdownRequest {
  string node_id = 1;           // 节点标识 "node-detect"
  int64 timestamp_ms = 2;       // 发送时刻（毫秒时间戳）
  NodeStatus status = 3;        // 终态状态（应为 NODE_STATUS_SHUTTING_DOWN）
  string reason = 4;            // 退出原因（可选，如 "SIGTERM" / "exception" / "manual"）
}

message ShutdownResponse {
  bool acknowledged = 1;        // 服务端是否确认收到（A 侧不消费此值）
  int64 server_timestamp_ms = 2;// 服务端接收时刻
}

// ---- 节点工作状态枚举 ----
enum NodeStatus {
  NODE_STATUS_UNKNOWN = 0;       // 未知（默认值）
  NODE_STATUS_IDLE = 1;          // 空闲：等待推理请求
  NODE_STATUS_BUSY = 2;          // 推理中：前向推理占用 GPU
  NODE_STATUS_SHUTTING_DOWN = 3; // 退出中：正在清理，不再接新任务
}
```

格式选择理由：

- 图像用 **JPEG**：千兆局域网内原始帧带宽并非瓶颈，但 JPEG 可显著降低传输量与内存拷贝，且两侧编解码开销均可承受；RGB 采集分辨率 [待补充：开发时按 336L 实际配置确定]
- 掩码用 **PNG**：3 类掩码近乎二值图，PNG 无损且压缩率极高
- 请求携带 `camera_distance_mm`：距离标量随帧绑定发送至检测节点；检测节点 不在计算中消费该值，仅随帧记录，用于日志追溯与帧同步校验
- **响应追加 `status` 字段（捎带）**：业务 RPC 响应仅多 1 个 varint 编号字段（≈1 字节），零额外网络往返即可同步节点状态
- **心跳包极简**：仅含 5 个基础字段，protobuf 编码后约 30–50 字节，可塞入单个 TCP 包，链路层零分片
- **Shutdown RPC 独立于 Heartbeat**：退出通知是单次事件而非周期推送，与 Heartbeat 语义不同，故单独成 RPC；best-effort 语义——A 侧设 deadline=2s，超时/失败仅记 WARNING 日志不重试、不阻塞退出；B 侧收到后立即标记 A 离线并触发降级，无需等 15s 心跳超时；异常退出（崩溃/断电/网络中断）时 Shutdown 发不出，仍由心跳超时兜底

接口冻结说明：上述字段为原型阶段定稿；流式推理（InferStream）属 C 类要素，本阶段不实现；**双方向各自独立 channel，统一监听 50051 端口**——检测节点 的 grpc_server 在 A:50051 提供 Infer RPC（S→D），服务节点 的 grpc_server 在 B:50051 提供 Heartbeat + Shutdown RPC（D→S），双节点互为客户端/服务端，禁止复用同一 channel 承载双向调用；心跳间隔与超时阈值由 `config/network.json` 扩展字段（`heartbeat_interval_seconds` / `heartbeat_timeout_count`）配置，不硬编码。

### 5.6 帧同步机制

- **帧同步（强制要求）**：以 `frame_id`（单调递增）为主键、`timestamp_ms` 为辅助校验，严格保证同一帧的 **RGB 原图、距离标量、类别掩码三者一一对应**；服务节点 仅在三者标识一致时执行测量，标识不符、迟到或缺失的帧一律丢弃
- **请求配对**：响应与请求按 `frame_id` 匹配；乱序、迟到响应直接丢弃，不做重排
- **超时控制**：gRPC 客户端设置 deadline；超时帧跳过，不阻塞采集主循环
- **健康检查**：服务节点 运行中定期探测检测节点 存活性；推理服务不可用时系统降级为"仅视频 + 激光"模式并在界面提示（与 §4.3 降级模式一致）

### 5.7 节点状态监测与反馈机制（全局架构）

#### 5.7.1 机制定位与设计哲学

节点状态监测与反馈机制是双节点系统的"生命体征监护仪"——以**最小的资源代价**，让服务端（服务节点）始终掌握推理端（检测节点）的实时健康状态。

**核心设计原则**：

| 原则 | 说明 |
|------|------|
| **极简数据包** | 心跳包仅含 ≤5 个基础字段（protobuf 编码后 ≈ 30–50 字节），单包塞入一个 TCP segment，链路层零分片 |
| **发送者异步非阻塞** | 检测节点 侧心跳发送在独立 daemon 线程执行，队列满或网络抖动时不阻塞推理业务 |
| **仅 Node A 主动推** | 状态监测严格遵循"A 推 B 收"单向模式；检测节点 不处理 B 的任何反馈（无请求-响应语义外的耦合） |
| **服务端兜底判定** | 服务节点 侧通过"心跳超时"作为兜底手段——检测节点 退出通知失败时，超时机制仍可判定离线 |
| **共用通信通道** | 心跳 RPC 复用现有 gRPC 端口（50051），不引入新端口或新协议栈 |

#### 5.7.2 三种低开销子手段（逻辑解耦）

| 方向 | 手段 | 触发时机 | 开销级别 | 说明 |
|------|------|----------|----------|------|
| A → B | **3. 心跳保活（KeepAlive）** | Node A 后台线程周期推送（默认每 5 秒） | 极低：30 字节 / 5 秒 ≈ 6 B/s | 仅携带节点标识、时间戳、状态枚举；"我活着" |
| A → B | **2. 退出通知（Shutdown RPC / Best-effort）** | Node A 退出前（正常 SIGTERM / 异常捕获） | 极低：单次 | 一次性"我要下线了"；经 grpc_client 调用 Shutdown RPC，deadline=2s，失败不阻塞退出 |
| A → B（内嵌） | **1. 状态捎带（Piggybacking）** | Node A 回复 InferResponse 时内嵌 status 字段 | 零额外 RPC；每响应 +1 字节 | B 侧在处理业务响应时顺便更新状态，与心跳互补 |

#### 5.7.3 职责分工（强制解耦）

| 角色 | 检测节点（推理端 - 反馈端） | 服务节点（服务端 - 监测端） |
|------|--------------------------|--------------------------|
| **核心动作** | 采集状态 → 发送反馈 | 接收反馈 → 判定状态 → 记录事件 |
| **心跳** | 周期性推送 HeartbeatRequest 到 B | 写入超时计时器；超时则触发降级 |
| **退出通知** | 经 grpc_client 发送 Shutdown RPC（best-effort，deadline=2s） | 经 grpc_server 接收 Shutdown RPC，立即转交 NodeMonitor 触发降级（无需等超时） |
| **捎带状态** | 每个 InferResponse 携带 status | 解析 status，更新节点状态缓存 |
| **不做什么** | 不关心 B 是否收到、如何处理 | 不主动轮询 A（避免反向耦合） |
| **资源隔离优先级** | 推理业务 > 心跳 ≫ 退出通知 | 所有监测操作均为异步、非阻塞 |

#### 5.7.4 心跳参数与超时判定（推荐默认值，部署时可调整）

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 心跳间隔 | 5 秒 | 过短浪费带宽，过长延迟失效检测 |
| 超时判定阈值 | 连续丢失 3 次心跳（15 秒） | 扣除偶发抖动的影响 |
| 心跳失败策略 | 降级并保留最后已知状态 + 持续心跳尝试 | 频繁闪断场景下避免 UI 抖动 |

#### 5.7.5 与现有架构的衔接点

| 现有组件 | 衔接方式 |
|----------|---------|
| §4.3 启动自检 | Node B 启动时利用现有 `probe()` 探测 Node A 发现性；心跳在此之后接管持续监测 |
| §7.5 日志规范 | 所有状态变更事件按统一格式写入日志（节点标识 + 状态 + 时间戳） |
| §5.6 帧同步 | 心跳包复用 `frame_id` / `timestamp_ms` 语义约定，无需引入新字段名 |
| §3.3 配置管理 | 心跳参数（间隔、超时阈值）从 `config/network.json` 读取，不硬编码 |

#### 5.7.6 兜底策略总结

```
检测节点 正常退出：
   Shutdown RPC ──→  服务节点 经 grpc_server 收到 → 立即标记离线、触发降级

检测节点 异常退出（崩溃 / 断电 / 网络中断）：
   Shutdown RPC 未发出（或发送失败）
        ↓
   心跳停止  ──→  连续丢失 3 次心跳（15 秒）→ 超时降级
        ↓
   保留心跳重连机制：检测节点 恢复后心跳自动触发"恢复在线"
```

> **接口冻结说明**：Heartbeat RPC 与 HeartbeatRequest / HeartbeatResponse / NodeStatus 枚举为原型阶段定稿；心跳间隔和超时阈值等参数可由 `config/network.json` 扩展字段调整（见 §5.5 协议段描述）。

## 6. 传感器数据融合与交互规范

### 6.1 激光测距数据链路

数据链路：4 路 STP23L → S21C 主控（汇总）→ Type-C 串口 → 服务节点 `serial` 模块（解析 11 字节帧）→ 4 路 uint16 距离值（mm）。

帧解析沿用 `demo.py` 现有的 `SerialManager` / `SerialBuffer` / `LaserDataParser` 实现（已与 S21C 手册核对一致，见 §5.1）。

**热插拔持续扫描（已升级）**：`SerialManager` 以 `scan_interval_seconds`（默认 2.0 秒）为周期持续 auto_detect，发现 S21C 即自动连接；设备可随时接入/拔出（含换 USB 接口导致 `/dev/ttyUSB*`→`/dev/ttyACM*` 节点路径变化），断线后自动重新扫描重连，**无限重连**（`max_reconnect_attempts` 已弃用）。USB 稳定性监测（`usb_unstable_threshold`）在断线重扫时触发供电告警。

### 6.2 交互式融合策略（CLI 菜单）

4 路激光测距值融合为 1 个标量距离的逻辑由服务节点 通过**命令行终端交互（CLI 菜单）**实现，支持运行时动态切换：

| 选项 | 策略 | 说明 |
|------|------|------|
| 1（默认） | 取均值 | 有效路的算术平均值 |
| 2 | 取中位数 | 有效路的中位数值 |
| 3 | 取特定一路 | 用户指定接口编号（一~四），取该路值 |
| 4 | 手动输入指定值 | 用户直接输入距离值（mm），忽略探头数据 |

策略选择结果传递给 `measure` 模块，作为 `camera_distance_mm` 参与测量换算。策略在运行过程中可随时通过 CLI 菜单切换，切换后下一帧测量生效。

CLI 菜单的具体实现库 [待补充：建议 `argparse` 标准库以零额外依赖，或 `rich`/`click` 以提升交互体验，开发时确定]

### 6.3 数据有效性检查

无论采用何种融合策略，代码底层（`serial` 模块）在解析出 4 路距离值后、融合之前，必须执行以下检查：

1. **零值剔除**：距离值为 0 表示探头无回波或未连接，剔除并记录 WARNING 日志
2. **负值/异常值剔除**：距离值为负或超出物理量程的值剔除并记录 WARNING 日志。STP23L 量程为 0.07~7.5m（70~7500mm，80% 反射率白靶，见《STP-23L Datasheet》§4.1）
3. **全无效兜底**：若 4 路数据全部无效，融合结果置为 `None`，记录 ERROR 日志，当前帧测量不可执行，界面提示"激光测距无效"
4. **有效路数记录**：日志中记录每帧的有效路数与各路原始值，便于排查探头安装与接线问题

## 7. 工程与开发规范

### 7.1 代码风格

- 主语言 Python 3，遵循 PEP 8；注释、日志与 UI 文本使用中文（沿用现有约定）
- **模块化设计、高内聚低耦合**：各模块职责见 §3.1，模块间仅经明确接口交互，禁止跨模块直接读写内部状态
- 共享常量集中定义、单一来源，双节点禁止各自硬编码副本
- 所有值类参数从配置文件读取，严禁硬编码（见 §3.3）
- **配置文件统一 JSON 格式（强制要求）**：项目中所有项目侧编写的参数配置文件（`config/*.json`）必须统一使用标准 JSON 格式（双引号键、字符串值双引号包裹、无尾逗号、RFC 8259 合规），禁止使用 YAML、TOML、INI、自定义键值文本等其他格式存储项目参数。配置加载器统一使用 Python 标准库 `json` 模块解析（`json.load`），禁止引入 `pyyaml` / `toml` / `configparser` 等替代解析依赖。**唯一例外**：systemd `.service` unit 文件因 OS 规范强制要求 INI 格式，部署侧通过辅助脚本将项目维护的 JSON 参数源转为 systemd 所需的 INI 产物，不直接以 INI 充当项目参数输入源。

### 7.2 并发与 UI 约定（沿用现有）

- 基于线程的并发模型（非 asyncio），共享状态以 `threading.Lock` 保护
- 所有 tkinter UI 更新必须经 `root.after(0, ...)` 调度到主线程，子线程禁止直接操作 widget
- 绘制在主线程执行；子线程仅负责获取原始帧与传感器数据
- 启动流程：网络环境自检（§4.3）在 UI 前同步执行（**诊断模式，不阻塞**）；相机与 S21C 串口的扫描连接为软前置条件，在 UI 启动后异步进行（S21C 为**热插拔持续扫描**），失败可重试

### 7.3 依赖管理

- 按节点拆分依赖清单（检测节点：torch 等推理依赖；服务节点：opencv / pyserial / Pillow / 相机 SDK 等），避免在单板上安装无用的重依赖

### 7.4 测试策略（原型阶段从简）

- **节点级诊断**：沿用 `test_camera.py` / `test_gui.py`（已归档至 `temp/`）的思路，为两节点各配备硬件自检脚本（相机、串口、GUI、推理服务）
- **分阶段联调**：先各自独立验证（服务节点 挂本机 mock 推理服务 + 真实相机/串口；检测节点 用测试图片验证 gRPC 收发），再双节点整机联调
- 单元测试框架与覆盖率要求属 C 类要素，本阶段不引入

### 7.5 日志规范（一机一日志）

- **一机一日志**：检测节点、服务节点 各自维护**一个**全局日志文件（如 `logs/node_detect.log` / `logs/node_server.log`），节点内所有模块统一写入该文件
- **统一格式**（双节点严格一致）：`时间戳(毫秒) | 级别 | 节点 | 模块 | 消息`
  示例：`2026-07-30 14:23:01.125 | INFO | S | serial | S21C 帧解析成功: 4路距离=[812,815,810,813]mm`
- **统一级别**：DEBUG / INFO / WARNING / ERROR / CRITICAL，原型阶段默认 INFO 级
- **统一模块命名空间**：`camera`（相机采集）、`serial`（串口/激光）、`grpc_client`（服务节点 通信）、`grpc_server`（检测节点 通信）、`inference`（检测节点 推理）、`measure`（测量换算）、`ui`（界面交互）、`system`（启停与健康检查）
- 目的：跨节点对比调试时可按统一格式对齐两条时间线，尤其便于帧同步问题的排查

### 7.6 文件生命周期与归档管理规范

- **唯一归档目录**：项目根目录下设立 `temp/` 作为唯一指定的归档目录，用于集中管理废弃文件与历史版本。该目录同时用于存放临时中间产物，归档文件与临时产物共处一目录，便于统一管理与清理。
- **归档触发条件**：在后续的任何开发、重构或文档整理行动中，若产生以下文件，严禁直接物理删除（rm/del）：
  - 被新版本替代的旧文档或旧版设计草稿（如带 `_v1`、`_old`、`_draft` 后缀的文件）
  - 多 Agent 协作产生的中间态汇报文档
  - **虽然过时但具有重要里程碑/节点意义的中间过程记录**
- **归档操作**：必须将上述文件统一移动至 `temp/` 目录中，并建议在目录内维护一份 `_archive_log.md` 简要备注归档原因与时间，便于后续审计与回滚。
- **外部参考资料保护（禁止归档）**：任何外部硬件协议、API 手册、第三方说明文档（如 `orbbec-336L-win-protocol.md`、传感器 datasheet、主控使用说明等），属于项目开发的核心输入资产，**严禁**视为中间产物进行归档或修改，应保留在项目根目录或 `docs/` 目录下。

## 8. 关键约束与注意事项

### 8.1 性能与实时性

- Jetson Nano（Maxwell 架构 128 CUDA core，4GB 共享显存）算力有限：ResNet50-UNet @ 640×640 必须启用 CUDA（`new-predict.py` 已归档至 `temp/`，原实现固定 `cuda=False`，迁移时需启用 CUDA）；按"按需单帧"设计，不承诺逐帧实时
- 服务节点 的测量段为纯 CPU 传统 CV 运算（形态学、连通域、扫描线提取等），单帧耗时估计亚秒至秒级；在默认 3 秒触发间隔下属瞬时突发负载，对 ARM Cortex-A 不构成持续算力压力。工程约束：测量须在工作线程执行，完成后经 `root.after(0, ...)` 回主线程刷新显示，禁止阻塞 tkinter 主线程导致视频预览卡顿
- Nano 的 4GB 内存为 CPU/GPU 共享，模型加载后余量有限，检测节点 不应再承担其他服务
- 节点间传输建议有线千兆连接；Wi-Fi 仅作调试手段
- Windows 仅作为服务节点 上位机开发调试环境：摄像头后端 DirectShow（`cv2.CAP_DSHOW`），回退 MSMF

### 8.2 操作系统与平台兼容

- **Jetson Nano 系统环境（已确认）**：检测节点 已配置基于 Ubuntu 22.04 LTS 的 NVIDIA Jetson 官方定制内核 Linux，原生完全兼容 CUDA 生态，原镜像风险解除
- **openEuler**：tkinter 可能需单独安装（`sudo dnf install python3-tkinter`）
- **Linux 显示**：需设置 `DISPLAY`；SSH 调试用 `ssh -X`；Wayland 会话下程序自动设置 `GDK_BACKEND=x11` 兼容 tkinter，无 XWayland 时需 `sudo dnf install xorg-x11-server-Xwayland`
- **Linux 权限**：摄像头需将用户加入 `video` 组、串口需加入 `dialout` 组，配置后重新登录生效
- **串口芯片驱动**：S21C 主控 Type-C 串口芯片为 CH9102，Windows 调试环境需安装厂商驱动；Linux/openEuler 下一般可由内核 ch341 兼容驱动自动识别，首次接入服务节点 时实测确认

### 8.3 相机与标定

- **内参管理（已定稿）**：相机内参从**配置文件**读取（`config/intrinsics.json`，不硬编码于代码），以便快速适配硬件；默认焦距 fx=fy=`950`（沿用现有默认值），主点 cx/cy 一并纳入配置文件管理；后续由人工根据实际测试优化替换
- mm/px 换算直接依赖工作距离（激光测距值）与内参；测量数值的准确性由人工在后续阶段评估优化，原型阶段不作承诺

### 8.4 模型资产

- 推理依赖权重 `logs/Unet_resnet50.pth`：已准备妥当，为防止开发过程中损坏，刻意存放于代码目录之外，部署时按需获取（不入代码目录）
- 分割类别定义：0=背景，1=纵向钢筋，2=横向钢筋；推理侧与测量侧必须保持一致

## 10. 多 Agent 协作规范

### 10.1 协作能力声明

本项目**支持多 Agent 协作**（子 Agent 派发 / Worker / Task Delegation）。当环境支持时，优先采用多 Agent 模式并行处理复杂任务；当环境不支持时，降级为单 Agent 串行模式。

### 10.2 核心原则

- **最小上下文原则**：每个子 Agent 仅加载完成任务所需的最小上下文，禁止任何 Agent 一次性加载整个知识库。
- **任务传递仅含指令+路径**：Orchestrator 传递任务时仅含指令和路径，不传文档全文。
- **子 Agent 仅返回摘要**：子 Agent 完成后仅返回结果摘要或变更清单，**校验/推测结果写入 `_temp/` 目录**。

### 10.3 推荐分工架构

| 角色 | 职责 | 加载的上下文 |
|------|------|-------------|
| Orchestrator（主控） | 任务拆解、分发、汇总、校验调度 | 仅 `AGENTS.md` + 任务描述 + 本提示词 |
| Scanner Agent | 现状扫描与评估 | 仅目录结构 + 各文件首 20 行（或标题/摘要） |
| Verifier Agent(s) | 执行一致性校验与有限推测 | 仅目标模块代码/配置 + 对应文档片段 |
| Writer Agent(s) | 具体文档的创建/改写 | 仅目标文档相关的已有内容 + 约束段落 + `_temp/verify-*.md` 结果 |
| Indexer Agent | 创建/维护 `docs/INDEX.md` | 仅 `docs/` 文件列表 + 各文档标题摘要 |
| Auditor Agent | 执行全局更新校验流程 | 按步骤按需加载（见 §11） |
| Reader Agent（可选） | 代为查阅已有文档并返回摘要 | 仅加载被请求的单篇文档 |

### 10.4 单 Agent 降级策略

当环境不支持多 Agent 协作时：
- 串行执行，严格渐进式加载
- 每步仅加载当前步骤所需文件
- 若单篇文档过大，分段读取
- **校验/推测中间结果仍需写入 `_temp/` 目录**，保持流程可追溯

### 10.5 临时文件机制

- 每个子 Agent 将结果写入 `_temp/verify-*.md`（如 `_temp/verify-backend-deps.md`）或 `_temp/infer-*.md`
- 主 Agent 仅读取 `_temp/` 下的结果文件进行汇总，生成最终的可信度分层报告
- `_temp/` 目录为临时参考，非正式知识，供审计追溯

## 12. 可信度标签使用说明

### 12.1 标签体系

在项目背景、技术栈、架构概述等关键输出段落中，**必须**使用以下标签之一作为前缀，便于人工审阅时快速判断复核力度：

| 标签 | 含义 | 人工复核建议 |
|------|------|-------------|
| `[已校验一致]` | 文档描述与实际代码/配置完全吻合 | 低优先级抽查 |
| `[存在差异]` | 文档与实际不一致，已按实际修正 | **高优先级复核** |
| `[推测]` | 无直接文档，基于客观线索推断 | 中优先级确认 |
| `[推断]` | 基于多处间接证据综合得出 | 中优先级确认 |
| `[待补充]` | 无任何线索，无法推测 | 需人工介入 |

### 12.2 使用场景

- **README.md**：关键信息旁标注可信度标签（如 `技术栈：Python 3.11 + FastAPI [已校验一致]`）
- **docs/INDEX.md**：每条文档记录含"可信度"状态字段
- **docs/*.md**：每篇开头含可信度标签
- **校验/推测产物**（`_temp/*.md`）：每条结论必须带标签

### 12.3 自适应推测边界

当关键信息无文档说明或说明不完整时，允许基于有限线索进行推测，但必须严格遵守以下边界：

- **允许推测的范围**（仅限）：
  - 项目核心功能/用途（What it does）
  - 运行环境与部署目标（Where it runs）
  - 技术栈与框架版本（Tech stack）
- **禁止推测的范围**（红线）：
  - ❌ 业务逻辑细节、算法实现原理
  - ❌ 未来规划、Roadmap
  - ❌ 团队分工、负责人信息
  - ❌ 未经验证的性能指标、安全声明
- **推测依据**：仅可基于目录命名规范、代码注释、依赖清单、配置文件字段、Git 提交信息等**客观痕迹**
- **标注要求**：所有推测内容必须显式标注 `[推测]` 或 `[推断]`，并注明依据来源
